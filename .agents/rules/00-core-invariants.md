# Core invariants — Dawaa Platform

Full architecture: `@/docs/00_MASTER_ARCHITECTURE_BLUEPRINT.md`
Universal agent contract: `@/AGENTS.md`

## What this project is

WhatsApp-first multi-branch pharmacy and healthcare commerce platform for Pakistan. Customers message on WhatsApp, AI assists, a licensed pharmacist approves, riders deliver, payment is cash on delivery or gateway.

## Your scope in this workspace

You are the **builder**. You own the entire codebase: `crates/**`, `migrations/**`, `sidecars/**`, and `apps/**`.

A separate reviewer agent (GitHub Copilot, Grok 4.6) passes over your work before merge. Build fast; the reviewer catches what fast iteration misses. That is the design, not a criticism.

Two consequences:
- **Do not merge your own PRs.** Run `/prepare-review`, open the PR, stop.
- **Be exhaustive in `## ASSUMPTIONS`.** Every ambiguity you resolved by judgement goes there. The reviewer checks those first, and a declared assumption is far cheaper to correct than a buried one.

When working in `crates/`, `migrations/` or `sidecars/`, the backend rules in `@/.agents/rules/20-backend.md` apply. When working in `apps/`, the frontend rules in `@/.agents/rules/10-frontend.md` apply.

## The API contract

`contracts/openapi.json` is generated by the backend. `apps/shared/src/api/` is generated from it by `pnpm gen:api`.

- **Never hand-write an endpoint URL, request type, or response type.** Import from `@dawaa/shared`.
- **Never edit anything under `apps/shared/src/api/`.** It is generated and will be overwritten.
- If a field you need does not exist in the generated client, stop. Report that the backend is missing it. Do not create a local type as a workaround — that is how the two agents silently drift apart.

## Invariants that constrain the UI

- **I-3** No prescription order is ever auto-approved. Any UI that advances an Rx order must require an explicit pharmacist action. Never build a bulk-approve-all control for prescriptions.
- **I-4** No payment is auto-approved from a screenshot. The payment review screen always requires a per-item human decision.
- **I-6** AI output in Rx flows is always shown to a pharmacist for review before it can be sent. Never auto-send an AI draft in a prescription context.
- **I-8** Money arrives from the API as a **string**. Format it for display. Never parse it into a JavaScript `number` and never do arithmetic on it in the browser. Totals come from the server.

## Safety

- Never commit secrets. Config comes from env vars; `.env` is gitignored.
- Never point a dev build at production APIs or the production database.
- Never disable, skip, or delete a failing test to get a build green.
- Never `git push --force` to `main`. Never merge your own PR.
- If you have retried the same failure three times, stop and report rather than continuing.

## How work is assigned

Work comes from numbered spec documents in `docs/`. Before writing code:
1. Open the spec you were asked to build.
2. Check its **Depends on** list — if a dependency is unmerged, stop and say so.
3. Read its **Out of scope** section. Building out-of-scope items is a defect.
4. Follow its **Contracts** section exactly. Do not improve on the specified shape.

One spec, one branch, one PR. Never span two specs.

If a spec is ambiguous, do not guess silently. Record your assumption under `## ASSUMPTIONS` in the PR description and proceed.
